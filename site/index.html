CREED

CREED stands for C&IT Rules for Every Enterprise Developer. C&IT Rules for Every Enterprise Developer.

The standard everything rests on.

The Wayne State app stack's written standards: a handbook, plus policy.json, one file of support dates for PHP, Laravel, Node, MySQL, Vue and Inertia and the rules every check runs against. A small PHP reader answers the one question every tool asks: what state is this version in, on this date?

A The policy 23:57

  1. Every tool reads policy.json through the CREED reader. No other code decides whether a version is active, security-only or EOL.

    Why: two tools with two copies of a date will eventually disagree.

  2. A bad date, a wrong type or an unknown key fails the build. PolicySchemaTest and composer validate-policy both check it.

    Why: a typo in a date silently changes what every tool reports.

  3. Dates are YYYY-MM-DD. “Q3 2027” is not a date the schema will take.

    Why: tools compare dates as strings, and a vague date cannot be compared.

  4. A version with no security_until is an error, not a silent pass. So is an unknown component or version. Track length: 4:04, not found.

    Why: a tool that guesses turns missing data into a green check.

  5. Still supported on its security_until day, EOL the next, and past grace after eol_grace_days (90).

    Why: everyone must get the same answer on the same day, including on the boundary.

  6. The apps' PHP floor moves from ^8.2 to ^8.3 on 2027-01-01.

    Why: it is the only way a dependency floor can force an upgrade.

  7. No gate depends on a language model's opinion. A model may explain a failure; it does not decide pass or fail.

    Why: a gate must give the same answer twice.

B Your app 25:28

  1. Apps declare and run a PHP version that php.net lists as supported. The single, as promised on the sticker.

    Why: an EOL branch receives no security fixes.

  2. Security-only warns now and fails the day after security_until. Plan the move before then.

    Why: moving on a deadline day is how upgrades go wrong.

  3. composer.lock lives in the app's repository, and CI runs composer install, so everyone gets the same versions.

    Why: without a lock, a build next week is a different build.

  4. No dev-* branches and no * on runtime dependencies. Use carets, such as ^2.4.

    Why: an open constraint lets an unreviewed change into production.

  5. composer audit --locked in CI fails at or above the policy threshold: high.

    Why: known advisories are the cheapest attacks to run.

  6. An override sits in the app's policy-overrides.json with a reason and an expiry, and every run prints it.

    Why: an exception without an end date becomes the rule.

  7. CREED's own CI runs on PHP 8.3, 8.4 and 8.5, from its floor up.

    Why: a library that works only on the newest PHP leaves out half its users.

  8. git.wayne.edu has no runners today. Every product in the stack strongly recommends a git.wayne.edu instance runner. Like some people's pasts, it isn't printed on the sleeve.

    Why: a gate that nothing runs protects nobody.

Inner sleeve

Liner notes

One file

Most standards live in a document nobody can test. CREED's live in policy/policy.json: support dates for PHP, Laravel, Node, MySQL, Vue and Inertia, plus the rules every check runs against. A schema checks the file on every pipeline, and the handbook says the same rules in words, chapter by chapter.

No other code in the stack decides a version's state. PROCTOR, ADVISOR, BOOSTER and ROLLCALL ask; CREED's reader, Waynestate\Creed\Policy, answers. It is framework-free PHP with one dependency, and it never guesses.

With Arms Wide Open

The support window stays open until security_until. A version is still Security on that day, moves to Eol the day after, and stays there for eol_grace_days (90) more days before it is EolGraceExpired. The boundary is inclusive. Try it in the reader: pick the last day of PHP 8.2, then the day after.

Higher

CREED itself requires PHP ^8.3, like every stack package, and CI tests it on 8.3, 8.4 and 8.5. The floor for apps is a different number: ^8.2 until PHP 8.2 reaches end of life on 2026-12-31, then ^8.3. Creed has always been one version ahead of everyone else, at least by his own account.

Notes by the reader, which can account for every date it has ever had. Some quality assurance professionals cannot.

Quick start

A Install the reader

Any OS with PHP 8.3 or newer and Composer.

$ composer require waynestate/creed 
use Waynestate\Creed\Policy;

$policy = Policy::bundled();

// What state is PHP 8.2 in, on this date?
$policy->stateOf('php', '8.2', new DateTimeImmutable('2026-10-27'));
// State::Security

// What is the oldest PHP an app may declare?
$policy->oldestSupported('php', new DateTimeImmutable('2026-10-27'));
// '8.2'

B Run the checks

In a clone of CREED. With PHP and Composer installed, one command runs the whole gate:

$ composer ci

No PHP on the machine? Docker runs the suite and the schema check.

PowerShell, with Docker Desktop.

PS> docker run --rm -v "${PWD}:/app" -w /app composer:2 composer install --no-interaction
PS> docker run --rm -v "${PWD}:/app" -w /app php:8.4-cli vendor/bin/phpunit
PS> docker run --rm -v "${PWD}:/app" -w /app composer:2 composer validate-policy

Terminal, with Docker Desktop.

$ docker run --rm -v "${PWD}:/app" -w /app composer:2 composer install --no-interaction
$ docker run --rm -v "${PWD}:/app" -w /app php:8.4-cli vendor/bin/phpunit
$ docker run --rm -v "${PWD}:/app" -w /app composer:2 composer validate-policy

Any shell, with Docker Engine.

$ docker run --rm -v "${PWD}:/app" -w /app composer:2 composer install --no-interaction
$ docker run --rm -v "${PWD}:/app" -w /app php:8.4-cli vendor/bin/phpunit
$ docker run --rm -v "${PWD}:/app" -w /app composer:2 composer validate-policy

Maintainers refresh the patch numbers from the upstream feeds with php bin/refresh-patches.php --dry-run (drop --dry-run to write).
